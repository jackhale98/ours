## Summary

The cryptography is sound. The RFC 8291 and RFC 8292 code matches the RFCs and the RFC test vector. The endpoint allowlist held against every bypass tried. Authorization on the new routes is correct: you can only notify members of your own space, and you can only set reminders for yourself. The main problem is on the client: reminders for **private ("busy") plans** are sealed under the **shared space key**. That breaks the scope rule the codec exists to enforce. A curious or compromised server can then show a private plan's title, time and place on the partner's phone. The other two conditions are about availability. The per-minute cron is a single global queue of 100 that one or two accounts can fill. Delivery errors, including platform limits, are counted against innocent users' subscriptions, which are then deleted.

## Findings

### H1 (High): reminders for private plans are sealed under the shared space key

- **Location:** `apps/web/src/account/notify.ts` `plannedReminders()` (l. 267) and `sealFor()` (l. 195); `apps/web/src/app/sheets.tsx` "Remind me" (l. 436–468).
- **What happens:** `plannedReminders` iterates over every visible event with `remind[me]` set. It has no privacy filter, so it includes the user's own `privacy: 'busy'` events, which are scope `user` and sealed only under the personal key. Each reminder's title, time and **location** is then sealed with `ctx.ring.currentSpaceKey(spaceId)` and uploaded to `reminders`. The "Remind me" control is shown on busy events too. This bypasses the invariant in `codec.ts` ("private content cannot be sealed under the shared space key by an app bug") that THREAT_MODEL lists under integrity against the server.
- **Impact:** the partner holds the space key, and the server holds the ciphertext. THREAT_MODEL promises private records are protected from the partner, and from a curious or compromised server. Either of these breaks that promise:
  - A server that delivers a stored reminder to the partner's subscriptions (the server picks the target, and nothing in the payload names the recipient; see I3). The partner's service worker decrypts it and shows "Doctor · 15:00 · Clinic" as a normal notification.
  - A database copy combined with the partner's key, or a *former* partner's key: rotation is phase 7.
- **Recommendation:** seal reminders for user-scope records under the **personal key**, with a separate notify AAD scope such as `notify|user|<user_id>|version`. Have the service worker try the personal key for that scope. Alternatively, put only a generic "Reminder" under the space key for private plans. Enforce this in core, not the app: for example, `sealNotification` takes the source record's scope and refuses `user` with a space key. Add a unit test covering a busy event with a reminder. Also see I3: binding the recipient's user id into the sealed body (or AAD) and checking it in the service worker would block the delivery path.

### M1 (Medium): the reminder cron is one global queue that a single account can fill

- **Location:** `apps/api/src/routes/push.ts` l. 236–242; `apps/api/src/push/send.ts` `sendDue` (l. 183–223).
- **What happens:** `PUT /push/reminders` accepts up to 64 items per space, 120 times an hour. Items with `fire_at` down to `now − 60 s` are stored, so they are all due at once. `sendDue` sends at most 100 rows a minute (6,000/h) for the **whole instance**, ordered by `fire_at`, with no fairness per user. In probe P2, two accounts each stored 64 reminders dated `now − 59 s`. The next run sent 100 pushes, all to the attackers, and none to a victim's reminder that was due 10 s earlier. One account can enqueue about 7,680 due-now rows an hour, more than the cron can drain, and rows more than 1 h late are silently discarded. Each row also fans out to every subscription the target has (up to 10), all signed with the operator's VAPID key. Push services may throttle or block that key, which would affect every user.
- **Impact:** any user with an account (sign-up is open) can delay or suppress other users' reminders and quiet-hours notifications, and spend the operator's push reputation.
- **Recommendation:**
  - Require `fire_at ≥ now + 60 s`. The client never needs past reminders.
  - Cap reminders per user across spaces.
  - Charge the rate limit per stored item (or per delivery), not per PUT.
  - Make the cron fair, for example by taking at most N rows per `target_user_id` per run (`ROW_NUMBER() OVER (PARTITION BY target_user_id ORDER BY fire_at)`).
  - Size the batch to what one invocation can do (see M2), and loop or fan out (Queues) instead of using a fixed LIMIT 100.
  - Add a regression test like P2.

### M2 (Medium): claim-before-send plus failure counting loses reminders and deletes healthy subscriptions

- **Location:** `apps/api/src/push/send.ts` l. 83–131 (status 0 on any thrown error counts as a failure; 10 failures delete the row) and l. 200–223 (rows deleted before sending).
- **What happens:** each due row is deleted up front, so a send that fails is never retried. Any exception from `fetch` is recorded as `status = 0` and increments `failures` on the target's subscription. So does any non-2xx other than 404/410, including 429 throttling from the push service. On Workers Free, one invocation may make 50 outbound fetches and use 10 ms of CPU. Each delivery costs an ECDH key generation, HKDF, AES-GCM and an ECDSA signature per subscription, so a batch of 100 rows × several subscriptions runs past those limits. The remaining fetches throw (or the invocation is killed), and those reminders are lost. With M1, an attacker can make this happen every minute, and each lost send counts a failure against an uninvolved user. P3 confirms that 10 thrown fetches delete a healthy subscription. The user's notifications then stop without notice until they reopen the app.
- **Impact:** silent loss of reminders and of other users' subscriptions. This is self-inflicted at modest scale on the Free plan that SELF_HOSTING targets, and it can be triggered on purpose through M1.
- **Recommendation:**
  - Count only definite push-service rejections (400, 403, 413) as failures. Treat thrown errors and 429/5xx as transient: no count, or back off.
  - For the cron, claim by marking `claimed_at` instead of deleting. Delete after a 2xx, and let a later run retry unclaimed or stale-claimed rows until the sealed `expires_at`.
  - Bound the work per invocation by subrequests, not by rows.
  - Document the plan limits in SELF_HOSTING.

### L1 (Low): re-subscribing with another user's endpoint deletes and reassigns their subscription

- **Location:** `apps/api/src/routes/push.ts` l. 99 (`DELETE FROM push_subs WHERE endpoint = ? OR device_id = ?`).
- **Impact:** any account that knows a victim's endpoint URL can remove the victim's subscription and attach the endpoint to its own account with its own keys (P1). The pushes would then fail to decrypt in the victim's browser. This is denial of service, not disclosure. Endpoints are high-entropy and seen only by the browser, the push service and the server, so exploitation needs a leak. The cross-user replace exists so that a shared browser can switch accounts.
- **Recommendation:** allow taking over another user's row only when `p256dh` and `auth` also match, which proves the request comes from the same browser subscription. Otherwise return 409.

### L2 (Low): the deferred cap is shared by every sender and silently drops overflow

- **Location:** `apps/api/src/routes/push.ts` l. 183–197.
- **Impact:** the count of 20 is per target, across all spaces. During the target's quiet hours, a partner (or any space the target is in) can fill it, and later notifications are neither held nor sent. The response is `{queued: 0, deferred: 0}` (P5).
- **Recommendation:** count per `(target, space)`. When full, coalesce: keep the newest N, or replace the oldest. Return a distinct status so the client could retry.

### L3 (Low): silent pushes

- **Location:** `apps/web/src/sw.ts` l. 110 and l. 113.
- **Impact:** for payloads that fail authentication, or that are early, expired or duplicates, the worker shows nothing. Pushes are subscribed `userVisibleOnly`, and browsers penalise that: Chrome shows its own "This site has been updated in the background", and Safari revokes the subscription after a few silent pushes. A device with a wrong clock (beyond 5 min skew) or a delayed deferred push can lose its subscription without anyone noticing. A malicious server can do the same on purpose; that part is accepted, since availability isn't promised.
- **Recommendation:** in those branches, show the same minimal generic notification with `tag: 'ours-generic'`, so repeats collapse into one, or close it right after showing where the platform allows.

### L4 (Low): subscription and reminder lifecycle

- **Locations:** `apps/web/src/account/notify.ts` `disablePush` (l. 173–186); `session.ts` `signOut(false)`; no cleanup of `push_subs` for devices without a live session.
- **Impact:**
  - The server keeps one reminder list per **user** per space. Each device can replace it.
    - `disablePush` sends `items: []`, so turning notifications off on one device, or signing out there, deletes the reminders that the user's other devices rely on. Those devices won't re-upload until their plans change, because `reminders-sig` is unchanged.
  - `signOut(false)` (the 401 path) doesn't unsubscribe the browser.
    - If the device row still exists (expired session), the server keeps sending to it, and the wiped device shows "Something changed. Open Ours to see it." indefinitely. That reveals activity to whoever holds the device next.
    - A device whose session expired but which hasn't reopened the app still has its key ring, and keeps showing full decrypted notifications.
- **Recommendation:**
  - On disable or sign-out, don't clear the shared list. Make the list per device (key it by `device_id`), or have the server send to the user's subscriptions and let each device skip if it already has the list.
  - In `signOut(false)`, call `pushManager.getSubscription()?.unsubscribe()`.
  - In the service worker, unsubscribe when no key ring exists.
  - In the hourly cleanup, delete `push_subs` whose device has no unexpired session.

### L5 (Low): metadata not described in THREAT_MODEL

- **Locations:** `notify.ts` (no padding), `send.ts` (Urgency `high` for cron, `normal` for direct sends), reminder `fire_at`.
- **Impact:**
  - Notification ciphertext is not padded. The records use 64-byte buckets; notifications don't. The server and the push service learn the length of the title and body, such as a note's length, and can tell proposal from answer templates.
  - The push service (Google/Apple/Mozilla/Microsoft) can tell reminders from partner notifications by the Urgency header.
  - Reminder lead times are fixed (0/15/60/1440 min), and all-day plans anchor at 09:00 local. So `fire_at` reveals plan start times, private plans included, and the user's time zone even without quiet hours. THREAT_MODEL says only "reveals when reminders fire, not which plan". Also, every change in the plans re-uploads the list, which reveals when edits happen.
- **Recommendation:**
  - Pad the sealed notification JSON to a bucket (e.g. 256 bytes); RFC 8291 also allows padding.
  - Use one Urgency value.
  - Update THREAT_MODEL and the privacy policy to say that reminder times reveal approximate plan start times and time zone.

### L6 (Low): leaving or deleting leaves your deferred notifications queued

- **Location:** `apps/api/src/routes/spaces.ts` l. 46 (only rows *targeted at* the leaver are deleted); `reminders` has no sender column.
- **Impact:** after Sam leaves the space or deletes the account, notifications Sam sent during Alex's quiet hours are still delivered when those hours end (P6). The content is shared content under the space key, so this is minor. It does conflict with the expectation that leaving stops activity.
- **Recommendation:** store `sender_user_id` (it adds no new metadata, since the server already knows who called `/notify`). On leave or delete, delete the leaver's deferred rows, and clear the column on account deletion as in 0002 L5.

### I1 (Info): 500 on malformed base64

`pack()` calls `fromB64Url`, and `atob` throws on a length ≡ 1 (mod 4). The route then returns 500 instead of 422 (P4). Wrap it in a try/catch, or validate the length in the valibot schema.

### I2 (Info): `#accept=<id>` acts without confirmation

`App.tsx` `deepLink` (l. 45) accepts as soon as the hash matches. Any web page or message can link to `https://<app>/#accept=<id>`. Exploiting this needs the record id, which only the partner and the server know, and the partner can already write that record under the shared key. It adds nothing against the partner, but a URL shouldn't carry a state-changing action. Have the service worker pass the "yes" intent through `postMessage` or a one-time token in IndexedDB. Treat a bare `#accept=` as `#plan&open=`.

### I3 (Info): payloads are not bound to the recipient

The sealed body has no recipient or direction. The server can show a user their own message ("Sam asked: …" on Sam's phone), or send a user's reminder to the partner. That second path is what makes H1 exploitable. Add `to` (the recipient's user id, or `partner`/`self`) to the sealed body, and drop it in the service worker unless it matches this device's user.

### I4 (Info): `seen-nids` lost updates

Concurrent `push` events each read, modify and write `seen-nids`, so one id can be lost and a later replay of it would show again. `tag: nid` collapses simultaneous duplicates. Serialise the handler (a promise chain) or use an IndexedDB transaction.

### I5 (Info): config check

- `scripts/check-worker-config.mjs` checks the secret names only in top-level `vars`, not in `env.<name>.vars`.
- `VAPID_SUBJECT` falls back to `APP_URL`, which may be `http://…`. RFC 8292 requires `mailto:` or `https:`, and Apple rejects other values. Validate it at start-up.

## Verified correct

- **RFC 8291:** the key info `"WebPush: info\0" ‖ ua ‖ as`, the IKM with the auth secret as salt, the CEK and nonce labels, the header (salt, rs = 4096, idlen, 65-byte key id), a single record with delimiter 0x02, and a fresh ephemeral key and salt per message all match the RFC. The RFC Appendix A vector passes. The largest accepted payload (2,800 bytes, 64-char space id, 7-digit key version) encrypts to 3,934 bytes, under the 4,096 limit (P8).
- **RFC 8292:** ES256 with a raw r‖s signature, `aud` set to the endpoint origin, `exp` at now + 12 h (within the 24 h maximum), and `k=` the uncompressed public key. The private key must be a secret, and the config check forbids it in `vars`.
- **Endpoint allowlist:** HTTPS only, no port or credentials, and `redirect: 'manual'`. P7 tried uppercase, a trailing dot, IDN full-width dots (normalised to the same host), `\@`, a percent-encoded dot, an IPv6 literal, `:443` and punycode lookalikes; none got through. The allowlist is checked again at send time.
- **Authorization:**
  - `/notify` requires membership and targets only the other members of that space, or the caller.
  - Reminders are always written with `target_user_id` set to the caller.
  - No route reads reminders or subscriptions.
  - `DELETE /subscription` is limited to the caller's device and user.
  - The cron checks membership again before sending.
  - Deleting an account or revoking a device cascades to `push_subs` and `reminders`.
- **Cron claim:** the batched `DELETE` with `meta.changes` per row stops overlapping runs from double-sending (the existing test covers this).
- **Integrity:** the space id and key version are bound in the AAD. `not_before`/`expires_at` and the replay id are authenticated, and the server can't swap labels or spaces.
- **Client:** only ciphertext, `fire_at`, the time zone and quiet hours reach the server. Partner notifications are only sent for `privacy: 'full'` plans. The service worker validates `record_id` before building a URL. Messages from the service worker can only set the app's own hash.
- **`/dev/pushes`:** returns 404 unless `EMAIL_PROVIDER=dev-outbox` **and** the host is local (P9). The config check refuses `dev-outbox` in `vars`.

## Sign-off

**Do not sign off.** Re-review after H1 (private-plan reminders under the personal key, enforced in core, with a test), M1 (fair, bounded cron and no due-now reminders) and M2 (no failure counting for transient errors, retryable claims) are fixed. L1–L6 may follow before public launch.

### New findings

- **N1 (Low; residual of M1):** the cron is fair per run but not round-robin. In `apps/api/src/push/send.ts` `sendDue`, order the outer query by `n, fire_at` (each due user's first row, then their second, and so on). Then every due user gets a row each run as long as fewer than 40 are due, and starving others takes about 40 accounts with live subscriptions per minute instead of about 14. Add a test like R1. Consider a per-user cap across spaces as well: today it is 64 × 3 spaces.
- **N2 (Low, latent):** `apps/api/src/app.ts` `cleanup` uses `device_id NOT IN (SELECT device_id FROM sessions WHERE expires_at > ?)`. `sessions.device_id` is nullable, and one live session with a NULL `device_id` makes the predicate NULL for every row, so nothing is ever cleaned (R2). No current code path inserts NULL, so this is latent. Use `NOT EXISTS (SELECT 1 FROM sessions s WHERE s.device_id = push_subs.device_id AND s.expires_at > ?)`.
- **N3 (Info):** add a web unit test asserting that `syncReminders` seals with `currentPersonalKey()` and `scope: 'user'`, including for a `privacy: 'busy'` event. That is the regression H1 guards against, and today only the server-side and core tests exercise the scopes.
- **N4 (Info):** each delivery imports the VAPID JWK and signs a fresh JWT. With 40 per run on Workers Free (10 ms CPU), a run may be cut short. Rows are now retried, so this degrades rather than loses, but a row cut off three times is dropped. Sign one JWT per push-service origin per run, and **verify CPU time on the deployed Worker**.
- **N5 (Info):** at-least-once delivery means a rare duplicate after a crashed run shows the generic "Something changed" notice after the real one. This is acceptable; it is noted only so it isn't mistaken for a bug.

### Sign-off (re-review)

**Sign off with conditions:** (A) N1 round-robin ordering with a test; (B) N2 `NOT EXISTS`; (C) the owner checks on a deployed Free-plan Worker that a full 40-push cron run stays within the CPU limit (N4). N3 and N5 are optional.
